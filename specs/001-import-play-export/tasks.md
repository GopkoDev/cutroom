# Tasks: Import, Play, Export

**Input**: Design documents from `/specs/001-import-play-export/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md),
[data-model.md](./data-model.md), [contracts/](./contracts/), [quickstart.md](./quickstart.md)

**Tests**: Test tasks ARE included. They are not optional here: the slice exists to prove
properties that cannot be judged by looking at the screen (A/V drift over ten minutes, export
matching Preview, sound surviving CPU starvation), and `quickstart.md` names those checks as
gates.

## Numbering

IDs are sequential with no gaps and no letter suffixes: `T001`, `T002`, … Inserting a task
renumbers everything after it, and every reference to a task — the dependency graph, the parallel
sets, the MVP scope, quickstart.md, checklists/requirements.md — is rewritten in the same change.

This is stated because it was broken twice: tasks added after the first numbering were given
letter suffixes to avoid the renumbering churn, and both times the list stopped being sequential. The churn is the cost of the convention, not a reason to abandon it. Renumber with a
single mapping applied in one pass, or the shifts overlap and land on each other.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies on incomplete tasks)
- **[Story]**: Which user story this task belongs to (US1, US2, US3)
- Paths follow the monorepo layout in plan.md

### The model (`packages/model`)

- [x] T015 [P] Implement the Timebase module in `packages/model/src/timebase.ts`: `frameToSeconds`, `secondsToFrame`, `frameToSampleIndex`, `framesForDuration`, `frameToSourceTime`, with exact ratios throughout and total functions that throw on invalid input (contracts/model-api.md). `frameToSourceTime` is what makes a Source whose Timebase differs from the Project's someone else's problem exactly once — `packages/engine` calls it instead of doing rate arithmetic of its own (R7) — **done**: every conversion is a rational in BigInt collapsed to a Number once, at the end, so no intermediate float exists to carry error. Three rules the contract left open had to be decided and are now documented at their definition: `secondsToFrame` rounds to the nearest Frame with an exact half going **up**, so Frame n owns [n − ½, n + ½); `frameToSampleIndex` uses that same tie rule; and `framesForDuration` **rounds up**, because a count of n means the indices 0…n−1 — a 10.000 s Source at 29.97 is 300 Frames, index 299 starting at 9.9766 s, inside the file; only index 300, the exclusive end nobody decodes, would sit past it. (This corrected an off-by-one: the first implementation truncated to 299 and threw away a real Frame.) Invalid input is a `RangeError` naming the function, the argument and the value. Negative Frames and negative seconds are rejected rather than floored. `frameToSourceTime` deliberately takes no Source Timebase: a Source's time is seconds in its own timescale, so the mapping needs no rate arithmetic about the Source at all, and returning a reduced exact ratio means the engine inherits nothing to compound

The half-Frame cases are asserted on 32/1 and 2/1 Timebases so that every half-Frame boundary is an exactly representable double and the test pins the tie rule itself rather than a float artefact; the 29.97 cases sit just either side of the midpoint, where the answer is not float-dependent. Unknown fields are refused rather than dropped, since dropping them loses a future version's data on the next save. - [x] T019 Implement the migration chain in `packages/model/src/document/migrate.ts` with `CURRENT_SCHEMA_VERSION = 1`, a registry keyed by version, and refusal (not coercion) of documents from the future — **done**, with one deviation worth naming: the constant is *declared* in `types.ts` and re-exported here, because `parseProject` needs it to say "this document is from the future" and `migrateProject` needs `parseProject`, which would otherwise be a cycle. ### Storage (`apps/editor/src/storage`)

- [x] T026 [P] Implement the IndexedDB schema in `apps/editor/src/storage/db.ts`: a `projects` store keyed by id and a `source-links` store keyed by sourceId, with an upgrade path — **done**: one database, `cutroom`, at version 1, with both stores using **in-line keys** (`keyPath: "id"` and `keyPath: "sourceId"`) so a record cannot be filed under a key that disagrees with its contents. Three decisions worth naming. The database version is deliberately **not** the document's `schemaVersion` and is free to move independently: this number describes the shape of the stores, that one the shape of a document, and conflating them would make adding an index a migration of every Project. The upgrade path is ordered `if (from < n)` blocks rather than a `switch` with fall-through — same effect, and a browser that has never seen the database runs every block in order for free, so version 2 is one more block and nothing else. And the `projects` value is typed as no more than `{ readonly id: string }`: a stored record is *whatever version wrote it*, a document from an older or a newer build is a perfectly valid row, and typing it as `Project` would be a claim only `migrateProject` is entitled to make — `projects.ts` reads a row as untrusted input instead. The connection is a cached promise, not a cached database, so two callers racing on the first call get one connection; a failed open is not cached, and `blocked` / `blocking` / `terminated` are all handled, because the multi-tab deadlock they prevent is otherwise a hang with no error anywhere
- [x] T027 Implement the Project store in `apps/editor/src/storage/projects.ts`: list, load (through `migrateProject`), and save-on-transaction with debouncing (FR-020) — **done**, with four decisions. **Saving writes `parseProject(project)`, not the object handed in**: the model's own rebuild is what lands in IndexedDB, which makes it structurally impossible for a `FileSystemFileHandle`, a `Date` or a `Map` to reach the store — every one of them is structured-cloneable, so IndexedDB would have taken them without complaint and the document would have quietly stopped being portable JSON (ADR 0005, 0007). It also fails a document that would not survive its next load *now*, while the Project the caller holds is still intact, and it states no validation rule of its own: the check is the model's, in the model, once. **Listing is generous where opening is strict** — a summary is read field by field from an untrusted record, so a document this build cannot open is still listed (`openable: false`) and only `loadProject` refuses it; the list is where a user goes to recover, and one bad row that made `listProjects` throw would hide every Project they have. For the same reason there is **no IndexedDB index on `modifiedAt`**: an index silently omits records lacking its key path, so a Project whose timestamp went missing would vanish from the list rather than appear as one needing attention. Ordering is by `Date.parse`, not by string comparison, because `parseProject` accepts an explicit UTC offset and `09:00+02:00` sorts after `08:00Z` as text and before it as an instant. A migrated document is **not** written back on load: a load is not an edit, and rewriting would reorder a Project the user only looked at. The debounced saver's one hard property is that **the last Project handed to `save` is the last one written** — the loop re-reads what is outstanding *after* each write rather than before, so an edit whose debounce elapses while a write is in flight is picked up by that write when it finishes. Mutation testing earned its keep twice here: the first version of that test called `flush()`, which loops until the queue is empty and so passed against a deliberately broken saver, and the second still passed because the second edit's timer happened to fire after the write had finished — only holding the write open across both timers exposes the loss. `draining` is cleared by a `finally` on the promise rather than inside the async function, because with nothing outstanding that function completes synchronously and would clear the flag before the assignment that sets it, stranding a settled promise that `flush` would then await forever. A failed write is reported (`onFailure`, defaulting to the console) and not retried: every write carries the whole document, so the next save subsumes the lost one, while retrying spins forever on a document that will never be writable
- [x] T028 Implement the Source link table in `apps/editor/src/storage/source-links.ts`: put/get a `FileSystemFileHandle` by sourceId, query permission, request permission behind a user gesture, and verify a relinked file against the stored fingerprint (ADR 0005, FR-021) — **done**. No status is stored beside a handle: the three runtime states are derived on demand, because a stored answer is wrong the instant the user revokes access or moves the file. `querySourceAccess` and `requestSourceAccess` are separate functions rather than one with a flag, and `inspectSourceLink` — the call a Project's load path makes for every Source at once — is built only out of the first, so reopening a Project shows no prompt and does no file I/O at all; an e2e test counts the two calls apart and pins `requested` at zero. Both take the handle rather than a Source id, so the click handler that asks for permission can call it as its first act: an `await` before `requestPermission` is an opportunity for the browser to decide the gesture has expired. A granted permission is not a promise that the file is still there, so `readSourceFile` turns a throwing `getFile` into `offline / unreachable` — that is what stops a Preview showing pictures from a file that no longer exists (quickstart, Persistence step 7), and the row stays in the table so a Relink has somewhere to put its answer. **A Relink verifies `size` and corrects the name and `lastModified`**, which is the only rule under which both of data-model.md's sentences are true at once: it asks that a Relink check the picked file against `Source.fingerprint`, *and* that a Relink may legitimately correct that fingerprint and the name. A renamed file keeps its size and timestamp; a copied one keeps its size and usually gets a new timestamp; demanding both fields match would refuse every copied file — the commonest reason a Source goes Offline — and leave the "may correct its fingerprint" allowance describing something that could never happen, while demanding neither would let a Relink silently bind Clips to different footage. Quickstart's step 5 settles the name half: the file is *renamed* on disk and must still relink, so the name cannot be part of the check, and `Source.fingerprint` does not carry one. The handle is written only on success, so a mistaken pick cannot cost the user the good link they already had, and nothing here touches the `projects` store — asserted by a test that counts it still empty after a full link-and-Relink. Chromium's `queryPermission` / `requestPermission` are declared as optional members of a `SourceFileHandle` interface, since TypeScript's DOM library has neither; a browser without them is told so by name rather than being assumed to mean "granted" (ADR 0006). Tested in `apps/editor/e2e/project-store.spec.ts` and `e2e/source-links.spec.ts` — 14 specs in real Chromium, since Vitest's node environment has no IndexedDB and no structured clone of a file handle. The handles under test come from OPFS, which is only how a test obtains a real handle without a file picker Playwright cannot drive (the app copies nothing into browser storage, ADR 0005). What that leaves genuinely untestable, stated rather than faked: the `prompt` and `denied` permission states, which need a real picker grant to lapse from, and the Project list screen itself, which is T037

## Dependencies

**Phase order**: Phase 1 → Phase 2 → (Phase 3 → Phase 4 → Phase 5) → Phase 6

The three user stories are sequenced rather than parallel, because each depends on the previous
one's machinery: US2 needs the Frame-to-Source mapping and the compose path built in US1; US3
renders through the same path US1 and US2 established and mixes audio with the graph US2 built.
They remain independently *testable* and independently *demonstrable*, which is what the slice
needs.

## Implementation strategy

**Standing rule, not a phase**: a decision meeting the ADR bar gets its entry in `docs/adr/`
*before* the code that depends on it lands, and a domain term the code introduces enters
`CONTEXT.md` in the same change that introduces it (constitution, Development Workflow). Neither is
deferrable to Phase 6 — an ADR written after the fact records a decision nobody could have argued
with, which is not what the rule is for. T094 verifies this happened; it is not where it happens.

**MVP scope**: Phases 1–3 (T001–T058, including T037, T055 and T057). That delivers a
Frame-accurate viewer of the user's own
footage, which already proves the riskiest half of the architecture: persisted handles, worker
decode, PixiJS compositing in a worker, and the Timebase discipline.

**Increment 2**: Phase 4. This is where the slice earns its keep — playback that degrades picture
rather than sound is the property everything later depends on.

**Increment 3**: Phase 5. Export closes the loop and validates Principle III by comparing exported
Frames against Preview renders.

**Stop-and-reconsider signals**: if T092 shows scrub latency far outside SC-003 on ordinary
footage, or T070 cannot be made to pass without restructuring, that is a finding about the design
and belongs in an ADR before more is built on top.
